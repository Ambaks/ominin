# Ominin

AI solutions for restaurants, decreasing their operating costs and facilitating
their operations.

## What this is

Ominin provides computer and AI solutions to restaurant businesses — think cost
tracking, forecasting, invoice processing, and back-office automation.

> **Tout client qui paie signe un contrat, et les tarifs deviennent révisables (2026-09-22, `main`, migration appliquée) :** aucune session Stripe ne peut plus naître sans une ligne d'acceptation écrite dans la même requête — les trois chemins qui engagent (ouverture d'offre, bascule sur la formule groupée, réouverture en mois offerts) signent avant d'agir. Trois documents versionnés vivent dans le dépôt (`frontend/lib/legal/documents`) — **CGV** (Annexe tarifaire engendrée depuis `lib/landing-data.ts` et `lib/shop-landing-data.ts`, plus un formulaire de rétractation), **accord de sous-traitance RGPD** et **politique de confidentialité** — publiés sur `/cgv`, `/sous-traitance`, `/confidentialite`, plus les `/mentions-legales` ; une seule copie de chaque sert tous les sous-domaines (`proxy.ts`, `rewriteOverrides` vers l'arborescence racine). **Base** (`20260922000001_contrat.sql`) : `legal_versions` (empreinte SHA-256, date d'effet, résumé), `legal_acceptances` et `etablissement_data_licence` (opposition à la réutilisation des données, table à part car `etablissements` est lisible par `anon`). **La preuve survit à ce qu'elle prouve** : `legal_acceptances` porte une colonne `scope` et recopie `signatory_email` et `scope_label`, et ses trois clés étrangères sont en `on delete set null` — supprimer l'établissement ou effacer le compte (art. 17 RGPD) laisse la ligne lisible, là où une cascade aurait détruit la preuve au moment précis où un client parti la conteste. **Le mécanisme juridique est tenu par le code, pas par la discipline :** l'empreinte d'un document couvre son annexe tarifaire **et sa date d'effet**, donc changer un prix — ou avancer la date d'application d'une version déjà publiée — change l'empreinte, et `npm run legal:publish` refuse de réécrire la version publiée : il faut une nouvelle version, avec sa propre date d'effet, donc son préavis de **30 jours** (`PRICE_NOTICE_DAYS`), que le script vérifie pour toute version autre que la première. La publication est **atomique** — tout est examiné avant qu'une seule ligne soit écrite, sans quoi une version refusée pour préavis insuffisant partait quand même en base et devenait applicable à sa date. Et le contrôle ne dépend pas du script : à chaque signature, le serveur recompare l'empreinte enregistrée au texte que le dépôt sert, et **refuse de faire signer** (503) si elles divergent — un déploiement qui oublie `legal:publish` échoue fermé au lieu de faire signer un texte que l'empreinte ne décrit plus. L'avis part **à la publication**, par e-mail (API Gmail) aux gérants et aux propriétaires de boutique, doublé d'un bandeau dans l'espace — y compris pour une première version applicable tout de suite, sans quoi les clients déjà servis découvriraient le contrat par un écran de blocage ; à la date d'effet, un écran d'accord, première signature et réacceptation ayant chacune son texte. Le verrou est monté dans les deux espaces, restaurants et boutiques. **Le verrou ne se ferme que sur une certitude** (textes publiés, non signés, signataire présent) : en panne, il laisse passer, et le personnel n'est jamais arrêté — couper la cuisine pour une formalité coûterait un service. Les dates d'effet sont posées à minuit **heure de Paris** (`parisEffectiveDate`) : en UTC, il existait deux heures pendant lesquelles aucune version n'était en vigueur et tout ce qui en dépend tombait. Côté données, l'article « Données et amélioration des Services » distingue les **données d'exploitation** (non personnelles : licence large, entraînement de modèles compris, survivant à la résiliation) des **données personnelles des convives** (anonymisées sur instruction documentée du Client, seul le résultat anonyme étant réutilisé), avec opposition depuis les réglages. Rétractation de **14 jours** accordée volontairement (`WITHDRAWAL_DAYS`, art. L221-3 C. conso.), Cachets imprimés exclus comme biens personnalisés. `STRIPE_TOS_CONSENT=1` ajoute le recueil de consentement côté Stripe, une fois l'URL des CGV renseignée au Dashboard. Vérifié : `npx tsc --noEmit`, `npm run lint`, `npm run build` propres ; la migration rejouée sur un Postgres local avec la surface Supabase simulée et un scénario de 17 contrôles (contrainte de portée, isolation RLS entre gérants et entre boutiques, lecture `anon` des versions et refus d'écriture, survie de la preuve à la suppression de l'établissement et à l'effacement du compte, `updated_at` au second choix, suppression de la licence refusée) ; les quatre pages servies en 200 avec leurs tarifs engendrés. **Limite connue** : `training_opt_out` est enregistré et respecté contractuellement, mais aucune chaîne d'anonymisation ne le lit encore — il n'y en a pas. **Mis en service le 2026-09-22 :** migration et types en production, identité de l'éditeur renseignée (EI dispensée d'immatriculation au RCS et au RM), versions `2026-09-22` des trois documents publiées et en vigueur — empreintes en base identiques à celles que sert le site —, avis envoyé aux 8 gérants et propriétaires de boutique. Les mêmes `NEXT_PUBLIC_OMININ_SIREN` / `_RCS` / `_ADDRESS` doivent figurer dans Vercel pour que `/mentions-legales` les affiche. Tant que ce dernier n'a pas tourné, les paiements répondent 503 — le refus est volontaire, mais l'ordre doit être tenu. Les documents demandent une relecture d'avocat sur deux points : la clause de révision des tarifs et l'annexe de sous-traitance.

Aucun délai ne la ramène en caisse : une addition que le client n'a pas demandé d'encaisser ne surgit jamais devant la salle (un premier jet la faisait reparaître après 31 min, retiré sur relecture — en salle, ça faisait une commande fantôme à encaisser une demi-heure plus tard). Le carillon (`use-order-chime`) ignore les commandes en attente de règlement en ligne et sonne quand elles arrivent pour de bon : au paiement (réglée, partie en cuisine) ou à l'abandon. **Menu QR** — `cart-bar` passe `p_online_payment: payment === "carte"` et ne prévient la salle en push qu'au choix comptoir ; tout échec de la carte (Stripe ou SumUp impossible à démarrer, Square sans point de vente, widget refermé sur « Payer au comptoir ») passe par `fallBackToCounter` (`lib/menu/online-payment.ts` : RPC d'abandon, puis push « Nouvelle commande »). `payment-return` abandonne dès le retour « annulé » ou « non confirmé » ; « Réessayer par carte » repasse par `/api/stripe/pay`, qui repose l'heure (comme `/api/sumup/pay`) et cache à nouveau la commande. Sur `checkout.session.expired` (31 min sans paiement ni choix du comptoir), le webhook connecté **supprime** la commande via `discard_online_payment` (annulation d'abord, pour que le trigger rende le stock, puis suppression : aucune trace, ni en caisse ni dans l'historique — une commande que personne n'a payée ni demandé d'encaisser n'a jamais existé pour le restaurant) ; une commande déjà passée au comptoir ou réglée n'est pas touchée. **Push** — au règlement effectif, `settleCheckoutSession` (Stripe), `confirmOrderPaid` (SumUp) et `settlePayment` (Square) appellent `dispatchOrderEvent(…, "nouvelle_commande")` ; `dispatchOrderEvent` accepte cet événement pour une commande sur place payée en ligne (`payee` ou `servie`) et compte son âge depuis la jambe `en_ligne` plutôt que depuis la création. > **Square, deuxième encaisseur du menu QR (2026-09-10) :** un restaurant peut désormais choisir Square plutôt que Stripe pour le paiement à table. L'intérêt n'est pas de doubler un fournisseur : c'est que le restaurant relie **son** compte Square — nous n'en créons aucun — et que Square pousse ensuite lui-même la commande réglée vers sa caisse et son Order Manager, où elle s'imprime avec ses réglages de ticket. Nous n'envoyons rien en caisse, nous constatons. Le socle multi-fournisseur existait depuis SumUp (jamais activé, scope `payments` toujours refusé) : `payment_provider` gagne une troisième valeur (`20260910000003_square_provider.sql`, isolée — `ALTER TYPE … ADD VALUE` ne se référence pas dans sa propre transaction), et `20260910000004_square.sql` ajoute `square_accounts` (jetons OAuth, RLS sans policy = service_role seul, comme SumUp), `etablissements.square_location_id` — délibérément **hors** de la table à secrets, le SDK carte le consomme dans le navigateur et le menu anonyme doit le lire dans le même aller-retour que la carte — et sur `orders` les références `square_order_id` / `square_payment_id` / `square_idempotency_key`. **Le catalogue n'est pas synchronisé** : Ominin reste la source de vérité du menu, les commandes partent avec des lignes ad-hoc (nom, prix, et le taux de `order_items.vat_rate`, posé en TVA `INCLUSIVE` puisque les prix sont TTC — c'est exactement ce pour quoi la colonne avait été ajoutée). **Paiement** : le SDK Web Payments tokenise la carte dans le navigateur (Ominin hors périmètre PCI), puis `/api/square/pay` fait `CreateOrder` — `ticket_name` « Table 7 », `reference_id` = l'id Ominin, une `fulfillment` PICKUP sans laquelle Square ne pousse rien vers la caisse — puis `CreatePayment`, pourboire en `tip_money` à part pour qu'il remonte dans le reporting pourboires du restaurant. Le montant n'est jamais fourni par le client : les lignes sont relues en base, et c'est le total calculé par Square qui devient le montant débité. **La fenêtre entre les deux appels** est fermée par quatre verrous : clé d'idempotence de commande déterministe (`sq-order-<id>`), clé de paiement persistée **avant** l'appel, jetons carte à usage unique côté Square, et relecture de la commande Square avant toute nouvelle tentative — une commande déjà réglée est close, pas re-débitée. Le webhook signé (HMAC-SHA256 sur URL + corps brut, vérifié avant tout parse ; 401 sinon, 500 sur échec transitoire pour que Square réessaie) reste le filet durable. **Jetons** : 30 jours de vie, donc `/api/square/refresh` (protégée par `CRON_SECRET`) renouvelle tout ce qui expire sous sept jours, appelée par le workflow quotidien `square-refresh.yml` — dont l'échec **est** le canal d'alerte, GitHub prévenant par courriel ; le rafraîchissement à l'usage reste la seconde ceinture, pour les comptes qu'aucune commande ne réveillerait. **Écrans** : le panneau « Paiement à table » cesse d'être codé en dur sur Stripe et demande d'abord l'encaisseur, choix verrouillé dès qu'un compte est relié ; un compte Square multi-sites fait choisir le point de vente auquel les QR codes appartiennent. La garde `enforce_online_payment_account` devient fonction du fournisseur (Square exige un compte **et** un point de vente ; `null` et `sumup` gardent le chemin d'aujourd'hui) et revalide sur changement de fournisseur ; délier un compte Square coupe la carte, pendant du trigger Stripe existant. CSP élargie aux hôtes Square (production **et** bac à sable, c'est là que le parcours se teste). Vérifié : `npm run lint`, `npm run build`, `npx tsc --noEmit` propres. **Reste à faire, dans l'ordre** : `supabase db push` (les deux migrations) ; créer l'application dans la Developer Console et renseigner `NEXT_PUBLIC_SQUARE_APPLICATION_ID` (public, lu aussi par le serveur — son préfixe `sandbox-` détermine l'environnement, ce qui évite un second réglage qui pourrait le contredire), `SQUARE_APPLICATION_SECRET`, `SQUARE_WEBHOOK_SIGNATURE_KEY`, `CRON_SECRET` (`.env.local` + Vercel) et les secrets `CRON_SECRET` / `MENU_URL` sur GitHub ; déclarer l'URL de redirection `https://menu.ominin.com/api/square/callback` et un abonnement webhook sur `payment.updated` + `order.updated` pointant `https://menu.ominin.com/api/square/webhook` ; **puis le parcours complet en bac à sable avant tout client**. Le test qui décide de tout n'est pas là : c'est, chez un pilote en service réel, de regarder l'écran de caisse et le ticket imprimé — si le personnel ne voit pas « Table 7 » au premier coup d'œil, le produit paraît cassé quelle que soit la qualité de l'intégration, et c'est cette réponse qui dira si le paquet Square se vend.

## Setup guide (written for an LLM agent)

If you are an AI coding agent asked to set this project up, execute the steps
below in order. Every step has a verification command — run it and confirm the
expected output before moving to the next step. Report any failures instead of
skipping ahead.

### 1. Prerequisites

Required: git, Node.js ≥ 20, Python ≥ 3.13, and [uv](https://docs.astral.sh/uv/).

```bash
node --version    # expect v20+
python3 --version # expect 3.13+
uv --version      # if missing: curl -LsSf https://astral.sh/uv/install.sh | sh
```

### 2. Frontend

```bash
cd frontend
npm install
npm run build     # must finish with no errors
```

Dev server: `npm run dev` → http://localhost:3000

### 3. Backend

```bash
cd backend
uv sync           # creates .venv and installs locked dependencies
cp .env.example .env
```

Ask the human for values for `.env` (Supabase keys, `ANTHROPIC_API_KEY`). The
server boots fine with them empty — they are only needed for features that call
Supabase or the Claude API.

Verify:

```bash
uv run uvicorn app.main:app --port 8000 &
sleep 3 && curl -s http://localhost:8000/health   # expect {"status":"ok"}
kill %1
```

Dev server: `uv run uvicorn app.main:app --reload` → http://localhost:8000
(interactive API docs at /docs)

### 4. Supabase (database & auth)

The schema lives in `supabase/migrations/` (schema → functions/triggers →
RLS). One-time human steps: create a free project at supabase.com, then copy
from Project Settings → API the URL + `anon` key into `frontend/.env.local`
(`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`) and the URL +
`service_role` key into `backend/.env`.

```bash
supabase login                          # opens browser once
supabase link --project-ref <ref>      # ref = id in the project URL
supabase db push                       # applies supabase/migrations/
cd frontend && npm run seed:demo       # inserts the Trattoria Lucia demo
```

Optional but recommended: regenerate the DB types after any schema change —
`supabase gen types typescript --linked > frontend/lib/supabase/database.types.ts`.
For Google sign-in, create an OAuth Client ID in Google Cloud Console and
enable the Google provider in Supabase → Authentication → Providers (use the
callback URL shown there).

The CLI above is your **own** free project for local dev — every contributor
creates one, no coordination needed. **Pushing to the actual production
project (`shop.ominin.com`, `admin.ominin.com`) is different: it is one
project shared by everyone, so you must first be added as a member** (Project
Settings → Team on supabase.com, added by whoever owns the org) before
`supabase link --project-ref <the production ref>` will do anything. The CLI
is a `devDependency` of `frontend/` (`npm install` pulls it in) — from
`frontend/`, `npm run db:login`, `npm run db:link -- --project-ref <ref>`,
`npm run db:push` and `npm run db:types` are shortcuts for the commands above
that already point `--workdir` at the repo's `supabase/` folder. `supabase
link` only writes to `supabase/.temp/` (git-ignored), so linking is local to
your machine and doesn't touch anyone else's setup.

Verify: set `NEXT_PUBLIC_MENU_HOST=menu.localhost:3000` in
`frontend/.env.local`, run `npm run dev`, then `http://localhost:3000` shows
the portal and `http://menu.localhost:3000/m/trattoria-lucia` shows the demo
menu from the database. On that same host, `/login` → sign-up → `/onboarding`
creates a working `/gestion` space.
